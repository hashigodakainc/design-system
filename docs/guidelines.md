# Hashigodaka デザインガイドライン

Hashigodakaのデザインに関する横断的な判断の正本である。ここには、複数のトークンや資産に
またがる構成規則、概念の区別、恒久的な運用判断だけを書く。

- 色・寸法・書体の値と、トークン単位の用途説明の正本は `tokens/*.json`
- ブランド資産の状態・用途・制約の正本は `assets/manifest.json`
- 成熟度と未決事項（暫定運用を含む）の正本は、各JSONの `status` と `pending` フィールド
- トークン一覧やパレットの人間向け表示は、`guidelines/` サイトがJSONから生成する

この文書には値（カラーコードや寸法）を再掲しない。色や寸法はトークン名で参照する。

## ブランドの意味

会社の存在意義、顧客との責任境界、人とAIの関係の正本は、Hashigodaka Wikiの
[ハシゴダカの存在意義とブランドの骨格](https://github.com/hashigodakainc/wiki/blob/main/company/brand-foundation.md)
である。この章は、会社の正本をデザイン、写真、図解、コピーへ翻訳するためのガイドである。
会社の意味を変更するときはWikiを先に更新し、その後にこの文書へ反映する。

### 中心命題

> **企業の意思に、AI時代の実装力を与える。**

ハシゴダカは、企業が持つ意思を、AIの力と専門家の経験によって、正しく速く成果へ変える
実装パートナーである。顧客が何を変え、誰に何を届けるかを決める。ハシゴダカは、その意思を
実装可能な形へ整理し、技術的な選択肢と制約を示し、合意した成果に必要な検証、開発、品質保証、
導入、定着を担う。

### デザインで表す構造

ブランド表現では、単発の「AI導入」や「速い開発」ではなく、次の循環を扱う。

```text
現実の変化を捉える
        ↓
人が考え、決める
        ↓
AIの力で形にする
        ↓
顧客や現場へ届ける
        ↓
フィードバックから学ぶ
        ↓
次の判断へ
```

写真、図解、モーションは、この循環の一部分または接続を一つの主張として見せる。すべての要素を
一枚へ詰め込まない。

### 人とAIの見せ方

- 人を、AIの利用者ではなく、意思決定と責任を持つ主体として描く。
- AIは、発光、粒子、回路、ロボットなどで擬人化せず、人の実装力を増幅する構造や結果として表す。
  粒子や光を使う場合は、固有モチーフの形と具体的な状態変化へ結び付け、AIらしさを足す背景装飾にしない。
- 「人が指示し、AIが一瞬で完成させる」という魔法の演出を避ける。
- 要件、実装、テスト、承認、提供など、成果へ責任を持つための現実的な仕事を見せる。
- AIへ任せながら品質を担保する仕組みは、整理された情報階層、接続、反復、ゲートなどで表現する。

### 顧客との関係の見せ方

- 顧客を受け身の被支援者として描かず、変えたい現実と届けたい価値を持つ当事者として扱う。
- ハシゴダカが顧客の事業戦略や進む方向まで代わりに決めるような表現を避ける。
- 「伴走」は抽象的な共感ではなく、顧客が決めた方向を正しく実装し、合意した成果へ到達する関係として表す。
- 自走化をすべての支援の結末にしない。ハシゴダカが継続的な開発組織になる支援と、
  顧客自身がAIを活用する力を得る支援の両方を扱う。

### コピーの基準

中心に置く言葉: 意思、実装、届ける、責任、変化、判断、循環、現場。

価値として説明すること:

- AIの可能性を、合意した成果へ変える
- 曖昧な意思を、実装可能な形へ翻訳する
- 速さとコストだけでなく、品質と継続性を両立する
- 人が疲弊せず、AIの成果に責任を持てる仕組みをつくる
- 企業が変化を捉え、決め、作り、届け、学ぶ速度を高める

避ける表現:

- AIを導入するだけで企業変革が完了する
- ハシゴダカが顧客に代わって事業の方向を決める
- すべての顧客を自走させる
- 「何でも作れる」「一瞬で完成する」など、判断と品質保証を省いた万能表現
- AIを使わなければ生き残れないと恐怖だけを煽る
- 生成量、ツール名、モデル名だけで先進性を示す

### 写真とキービジュアル

- 人物を使う場合は、会議のポーズではなく、観察、判断、設計、実装、レビュー、提供の実景を使う。
- 一人を主役にする場合は、その人の意思が複数の実装や業務へ展開される因果を見せる。
- 複数人を使う場合は、同じ対象へ働きかける具体的な協働を見せる。握手やカメラ目線で代用しない。
- システム画面を使う場合は、数を並べるだけでなく、誰の判断が何の成果へつながったかを構図で示す。
- 「変化」を表す場合は、派手な変身演出ではなく、捉える、決める、届ける、学ぶという連続性を見せる。
- コピーの背後へ写真やモチーフを置くときは、色、トーン、切り取り、面によって可読性を確保する。

### 既存コピーの扱い

「AIで人の可能性を、最大化する。」と「可能性を、動く仕組みへ。」は、コーポレートサイトの
制作過程で使われたコピーである。いずれも特定の画面では使用できるが、会社の存在意義全体を表す
確定コピーとして扱わない。キービジュアルでは、企業の意思、ハシゴダカの実装責任、変化へ応える
循環のうち、その画面で何を主張するかを決めてからコピーを選ぶ。

## ビジュアルの構成原則

- `color.neutral.canvas` を画面の基盤とし、最も広い面積を取る。色を画面全体へ敷き詰めない。
- `color.neutral.ink` は文字と必要な罫線へ使い、黒い大面積を既定にしない。
- `color.brand.primary` は、一つの強いグラフィックなど、意味のあるブランド表現へ絞る。
- `color.brand.secondary` とExtended Colorsは、Primaryより小さい面積で使う。
- 4つの有彩色を一つの画面で均等に使わない。図解で系列識別が必要な場合
  （`color.data.series.*`）を例外とする。
- ブランドカラーの面を黒枠で囲むことを共通スタイルにしない。色同士はCanvas相当の余白で分け、
  カードやスウォッチなど情報構造の境界には `color.neutral.border` を使う。
- Inkの強い輪郭は、Primaryボタン、キーボードフォーカス、文字やコード面など、意味のある箇所へ
  限定する。
- 写真、図形、大見出しを同時に主役にせず、余白で視線の順序を作る。

## カラーの使い方

- 制作物では、原色名ではなく `color.background.canvas`、`color.text.primary`、
  `color.action.primary.background` などの用途別トークンを参照する。将来パレットを調整しても、
  利用側の意図を保ったまま差し替えられるためである。
- ボタンのPrimary / Secondaryは行動の重要度を表し、ブランドのPrimary / Secondary Colorとは
  別の概念である。採用済みボタンはニュートラルカラーで階層を作る。
- 色付きバッジでは白文字を共通にするため、ブランド原色を直接使わず、コントラストを満たす
  バッジ専用の濃いトーンを使う。これらはブランドパレットの置き換えでも、Semantic Colorsでもない。
- コントラストの基準値と検査対象の組は `tokens/colors.json` の `contrastChecks` を正本とする。
- Primaryをリンク文字としてCanvas上へ直接置く用途は、現時点では承認していない。
- 色だけで状態や系列を伝えず、ラベル、形、線種などを併用する。

## タイポグラフィ

- 日本語を含む見出し、本文、UIは和文書体（`typography.family.*.body`）を使う。Soraは
  英字ワードマークと英字だけの表示の基準書体とする。
- 等幅書体はコード、変数名、ファイル名など、コードとして読む識別子だけに使う。小見出し、状態、
  日付を技術的に見せる装飾として使わない。
- 書体が変わっても情報階層が崩れないよう、利用側はフォント名や数値を直接指定せず、
  用途別クラス（`.hsg-type-*`）とトークンを参照する。
- 書体ペアはルート要素の `data-hsg-font-pair="di"` で適用する。未指定時もD-Iを使う。`hj` は
  過去の比較画面を再現する互換指定としてのみ残し、新しい制作物では使わない。
- 見出し階層は意味で選ぶ。見た目を小さくしたい理由だけで見出しレベルを飛ばさない。
- 標準本文の行長は和文35〜45字程度を目安にし、長文では段落を分ける。
- 太字、色、大きさの強調を同時に重ねず、情報の優先度に必要な一手だけを使う。

## レイアウト

- 余白は定義済みのスケール（`space.*`）から、隣接する要素同士の関係が伝わる最小の値を選ぶ。
  独自の中間値を追加する前に、要素のグループ分けや情報階層を見直す。
- 生の数値より、`layout.page.gutter.*` や `layout.section.space.*` などの用途別レイアウト
  トークンを優先する。
- コンテンツの最大幅は用途で分ける。本文・フォームなど読みやすさ優先の領域は
  `layout.content.width.reading`、一般的なページ本文は `layout.content.width.standard`、
  写真・図解・データ表など広さに意味がある領域は `layout.content.width.wide` を使う。
  画面幅が最大幅を超えても内容を無制限に引き伸ばさず、外側はページ余白として扱う。
- セクション間隔は装飾ではなく、話題の切り替わりと優先度を示す。すべてを最大にせず、同じ主題の
  内部は `layout.section.space.small` または `medium` でまとめる。
- ブレークポイント（`layout.breakpoint.*`)は端末を保証するものではなく、内容が窮屈になる地点で
  列数、配置、ナビゲーションを切り替える共通境界として使う。CSSカスタムプロパティは
  メディアクエリ条件へ使えないため、実装時の数値は `tokens/layout.json` と一致させる。
- レスポンシブ対応は縮小ではなく再配置として設計する。

## 固有モチーフ（01C-C）

状態、用途、制約、未決事項の正本は `assets/manifest.json`、SVG正本は
[`assets/motifs/01c-c.svg`](../assets/motifs/01c-c.svg) である。

### 形が担う意味

- 左右の厚い面と矩形に近い外周は、実装を担う力強さと単体マークとしての安定を表す。
- 中央を横断する青い接続は、Hの横画、橋渡し、共創を兼ねる。顧客の意思と実装、AIの可能性と
  現場の成果、現在地とまだ届かない場所の間にある断絶をつなぐ構造として扱える。
- 上下の曲線的なくびれは、蝶と、小さな意志が大きな変化へ波及するバタフライエフェクトを示唆する。
- 外側を直線的に、内側だけを有機的にすることで、D-Iの明快な文字骨格と人間味を両立する。

### 利用ルール

- 一つの面では原則として一つだけ使い、写真や別の大きな抽象図形と主役を競わせない。
- 単色で使う。既定は `color.brand.primary`、モノクロ要件では `color.neutral.ink`、暗い面への
  反転では `color.neutral.canvas` を使う。
- 縦横比を固定して拡大縮小する。回転、反転、輪郭線化、左右別色への分解はしない。
- 未検証の小サイズでは使わない。サイズの閾値と検証状況は `assets/manifest.json` の
  `restrictions` と `pending` を正本とする。小さく使う場合は中央の青い接続と上下の負形を
  実機で確認する。
- 会社名の「はしご」をそのまま図案化したものではない。社名の物語を説明するために、モチーフを
  梯子へ変形したり、段を描き足したりしない。意味を説明するために毎回モチーフ全体を見せる
  必要はない。
- SVGはインライン展開時に `color` で単色を差し替えられる。形状の `path` を複製して編集せず、
  正本のSVGを参照する。

### 採用済みのサイト固有例外

コーポレートサイトの一部セクションでは、全形を大きく拡大して画面端やセクション境界で切る
使い方を採用済みである。いずれも正本SVGの縦横比、向き、pathを維持したCSSマスクまたは
元SVG参照で実装し、切断面をコンテンツ領域へ侵入させず、本文より高いコントラストにしない。
これらの例外を、他の面で任意に切り取ってよい一般ルールへ拡張しない。具体的な寸法・配置は
各サイトの実装を正本とする。

## コンポーネント

採用済みコンポーネントの実装正本は `styles/components.css`（`.hsg-button`、`.hsg-badge` と
修飾クラス）である。

### ボタン

ボタンは、ブランドカラーではなくニュートラルカラーの面積と輪郭によって、行動の重要度を
3段階で示す。

- **Primary** — 画面内で最も優先する行動。原則として一つのまとまりに一つまで。Inkの背景、
  Canvasの文字（`color.action.primary.*`）。ホバーは階層を保ったまま黒のトーンを変える。
  例: 問い合わせを送信する、申し込みを確定する。
- **Secondary** — Primaryに次ぐ行動。Primaryと並置しても同じ強さに見せない。Canvasの背景、
  Inkの文字、Neutral Borderの枠線（`color.action.secondary.*`）。ホバーは明暗を反転する。
  例: 詳細を見る、別の方法を選ぶ。
- **Tertiary** — 補助的な行動や、現在の流れから戻る操作。透明背景、Inkの文字と下線
  （`color.action.tertiary.*`）。ボックス形状を作らない。ホバーは背景を付けず文字と下線を
  Mutedへ変える。例: 戻る、後で行う、補足情報を開く。

共通仕様:

- PrimaryとSecondaryの角丸は `radius.action` とし、矩形の明快さを保ちながら角の硬さだけを
  和らげる。ボックス形状を作らないTertiaryは角丸を付けない。
- ラベルはActionのタイポグラフィを使い、操作後の結果が予測できる具体的な動詞を選ぶ。
- キーボードフォーカスは `focus.outline.width` のInkアウトラインと `focus.outline.offset` の
  オフセットで示す。
- 色だけで階層や状態を伝えず、面・枠線・下線の形状差も保つ。
- `prefers-reduced-motion: reduce` では色のトランジションを無効にする。

未策定: 寸法バリエーション、Disabled / Loading / Successなどの状態、アイコン併用時の位置と
間隔、フォーム送信中の重複操作防止。

### バッジ

バッジは、短いラベルで状態、分類、段階を補助するコンポーネントである。本文の代わりに
重要情報を押し込まず、単体で意味が伝わる短い語を使う。

- 色付きバッジはすべて白文字を使う。ブランド原色へ白文字を直接載せるとコントラストが不足する
  ため、専用の濃いトーン（`color.badge.*`）を使う。Neutralだけは `color.badge.neutral.*` の
  Surface背景とInk文字を使う。
- Success、Warning、Error、Infoの意味はSemantic Colorsの策定後に割り当てる。現段階の色名は
  見た目のバリエーションであり、状態の意味を固定しない。
- 色だけに依存せず、「利用可」「未策定」など明確なテキストを必ず表示する。
- 黒枠を色付きバッジへ付けない。Neutralだけは背景との境界をNeutral Borderで示す。
