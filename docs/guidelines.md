# Hashigodaka デザインガイドライン

Hashigodakaのデザインに関する横断的な判断の正本である。成果物の生成時に行動を変える判断だけを
書く。値の正本は `tokens/*.json`、資産の正本は `assets/manifest.json`、成熟度と未決事項は
各JSONの `status` / `pending` フィールドを参照する。この文書には値（カラーコードや寸法）を
再掲せず、トークン名で参照する。

## ブランド表現の規則

会社の存在意義と責任境界の正本は、Hashigodaka Wikiの
[ハシゴダカの存在意義とブランドの骨格](https://github.com/hashigodakainc/wiki/blob/main/company/brand-foundation.md)
である。デザイン・写真・図解・コピーでは次を守る。

### 人とAIの見せ方

- 人を、AIの利用者ではなく、意思決定と責任を持つ主体として描く。
- AIは、発光、粒子、回路、ロボットなどで擬人化せず、人の実装力を増幅する構造や結果として表す。
  粒子や光を使う場合は、固有モチーフの形と具体的な状態変化へ結び付け、AIらしさを足す背景装飾にしない。
- 「人が指示し、AIが一瞬で完成させる」という魔法の演出を避ける。
- 要件、実装、テスト、承認、提供など、成果へ責任を持つための現実的な仕事を見せる。

### 顧客との関係の見せ方

- 顧客を受け身の被支援者として描かず、変えたい現実と届けたい価値を持つ当事者として扱う。
- ハシゴダカが顧客の事業戦略や進む方向まで代わりに決めるような表現を避ける。
- 「伴走」は抽象的な共感ではなく、顧客が決めた方向を正しく実装し、合意した成果へ到達する関係として表す。
- 自走化をすべての支援の結末にしない。

### コピー

中心に置く言葉は、意思、実装、届ける、責任、変化、判断、循環、現場。

避ける表現:

- AIを導入するだけで企業変革が完了する
- ハシゴダカが顧客に代わって事業の方向を決める
- 「何でも作れる」「一瞬で完成する」など、判断と品質保証を省いた万能表現
- AIを使わなければ生き残れないと恐怖だけを煽る
- 生成量、ツール名、モデル名だけで先進性を示す

過去のサイトコピー（「AIで人の可能性を、最大化する。」等）は特定画面の表現であり、会社を表す
確定コピーとして扱わない。

### 写真とキービジュアル

- 人物は、会議のポーズではなく、観察、判断、設計、実装、レビュー、提供の実景を使う。
- 複数人は、同じ対象へ働きかける具体的な協働を見せる。握手やカメラ目線で代用しない。
- 「変化」は派手な変身演出ではなく、捉える、決める、届ける、学ぶという連続性で見せる。
- コピーの背後へ写真やモチーフを置くときは、色、トーン、切り取り、面によって可読性を確保する。

## 色と面積

- カラートークンは、値を表す第1層（プリミティブ）、用途を表す第2層（セマンティック）、
  部品固有の第3層（コンポーネント）で構成する。制作物は第2層または第3層だけを参照し、
  `color.neutral.*` や `color.blue.*` など第1層を直接参照しない。
- 参照方向は第3層から第2層、第2層から第1層に限定する。第3層から第1層への直接参照は、
  対応する意味が第2層にない場合だけ許容し、同じ値を別の部品でも必要とした時点で第2層へ昇格する。
- `color.background.canvas` を画面の基盤とし、最も広い面積を取る。色を画面全体へ敷き詰めない。
- `color.background.raised` は、Canvas上では `color.border.default` の輪郭を伴う単発の面として使うか、
  `color.background.sunken` の区画内へ罫線なしで置く。面と罫線による境界表現を同じ要素へ重ねない。
- `color.background.sunken` の区画は入れ子にせず、内部の追加構造は罫線と余白で区切る。
- `color.background.inverse` はPrimaryの行動など意味のある箇所に限定し、一つのまとまりに一つまでとする。
- 通常の文字は `color.text.primary`、補足文字は `color.text.secondary`、罫線は
  `color.border.default`、フォーカスリングは `color.focus.outline` を使う。
- `color.brand.primary` は、一つの強いグラフィックなど、意味のあるブランド表現へ絞る。
  `color.brand.secondary` とExtended Colorsは、Primaryより小さい面積で使う。
- 4つの有彩色を一つの画面で均等に使わない。図解で系列識別が必要な場合
  （`color.data.series.*`）を例外とする。
- ブランドカラーの面を黒枠で囲むことを共通スタイルにしない。色同士はCanvas相当の余白で分け、
  情報構造の境界には `color.border.default` を使う。強い輪郭は意味のある箇所へ限定する。
- コントラストの基準値と検査対象の組は `tokens/colors.json` の `contrastChecks` を正本とする。
- Primaryをリンク文字としてCanvas上へ直接置く用途は承認していない。
- 色だけで状態や系列を伝えず、ラベル、形、線種などを併用する。
- 処理結果やシステム状態には `color.status.success.*`、`color.status.warning.*`、
  `color.status.error.*`、`color.status.info.*` を使う。ブランド色、Extended Colors、
  `color.badge.*` を状態色として代用しない。
- 状態メッセージは同じ状態のBackground・Foreground・Borderを一組で使い、状態名または具体的な
  説明と識別可能なアイコンを併記する。色だけで状態を伝えない。
- Successは完了または正常、Warningは確認や注意が必要、Errorは失敗または修正が必要、Infoは
  中立的な補足や案内に限定する。進行中や未確定をSuccessで表さない。

## タイポグラフィ

- 日本語を含む見出し、本文、UIは和文書体を使う。Soraは英字ワードマークと英字だけの表示の
  基準書体とする。
- 等幅書体はコード、変数名、ファイル名など、コードとして読む識別子だけに使う。小見出し、状態、
  日付を技術的に見せる装飾として使わない。
- 利用側はフォント名や数値を直接指定せず、用途別クラス（`.hsg-type-*`）とトークンを参照する。
- 見出し階層は意味で選ぶ。見た目を小さくしたい理由だけで見出しレベルを飛ばさない。
- 標準本文の行長は和文35〜45字程度を目安にし、長文では段落を分ける。
- 太字、色、大きさの強調を同時に重ねず、情報の優先度に必要な一手だけを使う。

## レイアウト

- 余白は定義済みのスケール（`space.*`）から、隣接する要素同士の関係が伝わる最小の値を選ぶ。
  独自の中間値を追加する前に、要素のグループ分けや情報階層を見直す。
- 生の数値より、`layout.page.gutter.*` や `layout.section.space.*` などの用途別レイアウト
  トークンを優先する。
- コンテンツの最大幅は用途で分ける（`layout.content.width.reading` / `standard` / `wide`）。
  画面幅が最大幅を超えても内容を無制限に引き伸ばさず、外側はページ余白として扱う。
- セクション間隔は話題の切り替わりと優先度を示す。すべてを最大にせず、同じ主題の内部は
  小さい間隔でまとめる。
- ブレークポイント（`layout.breakpoint.*`）は端末ではなく、内容が窮屈になる地点で構造を
  切り替える共通境界として使う。
- レスポンシブ対応は縮小ではなく再配置として設計する。
- 写真、図形、大見出しを同時に主役にせず、余白で視線の順序を作る。

## 固有モチーフ

用途・制約の正本は `assets/manifest.json`、SVG正本は
[`assets/motifs/brand-motif.svg`](../assets/motifs/brand-motif.svg) である。

- 一つの面では原則として一つだけ使い、写真や別の大きな抽象図形と主役を競わせない。
- 単色で使う。既定は `color.brand.primary`、モノクロ要件では `color.text.primary`、暗い面への
  反転では `color.text.inverse` を使う。
- 縦横比を固定して拡大縮小する。回転、反転、輪郭線化、切り取り、左右別色への分解はしない。
- サイズの下限は `assets/manifest.json` の `restrictions` を正本とする。
- 会社名の「はしご」をそのまま図案化したものではない。社名の物語を説明するために、モチーフを
  梯子へ変形したり、段を描き足したりしない。
- SVGはインライン展開時に `color` で単色を差し替えられる。形状の `path` を複製して編集せず、
  正本のSVGを参照する。

## コンポーネント

実装の正本は `styles/components.css`（`.hsg-button`、`.hsg-badge`、`.hsg-card` と修飾クラス）である。
見た目の仕様はCSSを読む。

- ボタンのPrimary / Secondary / Tertiaryは行動の重要度であり、ブランドのPrimary / Secondary
  Colorとは別の概念である。階層はニュートラルカラーの面積と輪郭で示す。
- Primaryは画面内で最も優先する行動に使い、原則として一つのまとまりに一つまで。
- ボタンのラベルはActionのタイポグラフィで、操作後の結果が予測できる具体的な動詞を選ぶ。
- 色だけで階層や状態を伝えず、面・枠線・下線の形状差も保つ。
- バッジは短いラベルで状態・分類を補助する。本文の代わりに重要情報を押し込まず、単体で意味が
  伝わる短い語を必ず表示する。色付きバッジはブランド原色でなく、白文字のコントラストを満たす
  専用トーン（`color.badge.*`）を使う。
- Neutral Badgeは周囲と反対の面を使う。Sunken面では `.hsg-badge-neutral-raised`、
  RaisedまたはCanvas面では `.hsg-badge-neutral-sunken` とし、罫線や影を加えない。
- Primary、Secondary、Violet、Orangeの色付きバッジは分類色自体が面を作るため、
  Raised / Sunkenへ分けない。
- カードは `.hsg-card` だけで使わず、面の役割に応じて `.hsg-card-raised` または
  `.hsg-card-sunken` のどちらか一つを必ず併用する。二つの修飾クラスを同時に使わない。
- `.hsg-card-raised` は周囲より前面へ持ち上がる独立した情報単位に使う。
  `color.background.raised` と `border.width.default` / `color.border.default` の輪郭で面を示し、
  影を重ねない。
- `.hsg-card-sunken` は周囲より奥まった補足情報、入力領域、内包された情報グループに使う。
  `color.background.sunken` で面を示し、罫線や影を重ねない。
- Raised / Sunkenは配置場所ではなくカード自身の面の役割を表す。列数や並べ方はカードへ
  固定せず、利用側のレイアウトで決める。
